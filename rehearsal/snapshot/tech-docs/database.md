# Database

## Approach

SQLite with EF Core (code first). Everything database-related lives in `GraderLogic/Data`: entities, `GraderDbContext`, migrations and `TestDataGenerator`. The original data model spec is `spec/2026-09-storyboard_erdiagram.md`; the entities and `GraderDbContext` are the current source of truth.

The development database is `data/grader.db` in the repository root. The `data` folder is committed (`.gitkeep`), its content is gitignored.

## Design decisions

- **All constraints are enforced by the database**, not only by EF Core: max lengths, unique indexes, foreign keys, check constraints. Anything that is not a database constraint (e.g. a validation attribute) does not count.
- **Where constraints are defined:** simple facets on the entity classes (`[MaxLength]`, `[Index(..., IsUnique = true)]`, required = non-nullable), everything else in `GraderDbContext.OnModelCreating` (check constraints, delete behavior).
- **No cascading deletes.** `OnModelCreating` sets `DeleteBehavior.Restrict` on every foreign key (`ON DELETE RESTRICT`). The loop must stay at the end of the method so it also covers relationships configured later. Deleting a referenced record fails; delete dependents explicitly first.
- **Migrations are generated and applied from `GraderLogic`**, which is both target and startup project. `GraderDbContextFactory` (an `IDesignTimeDbContextFactory`) creates the context for the tools; `GraderDatabase.GetDefaultConnectionString()` finds the repository root by searching upwards for `Grader.slnx`.
- **`dotnet-ef` is a local tool** (`dotnet-tools.json`, repo root) so its version matches the EF Core packages (EF Core ships with .NET and must match the SDK's major version).
- **Tests use a private in-memory SQLite database per test** (`GraderTests/Data/TestDatabase.cs`) created with `Migrate()`, not `EnsureCreated()`, so the tests also cover the migrations.
- **Test data** (`TestDataGenerator`) refuses to run on a non-empty database. It takes a `TimeProvider` (the current year determines the school years) and an optional seed for reproducible data. Percentages are normally distributed around 75 with the standard deviation chosen so that 10 % are at least 90, clamped to 0–100.

## Commands

Run in `GraderLogic` (`dotnet tool restore` once per clone):

```bash
dotnet ef migrations add <Name> --output-dir Data/Migrations
dotnet ef database update
dotnet ef migrations remove
```

## Gotchas

- **Commit a migration with every model change.** `Migrate()` throws if the model has changes that no migration covers (`PendingModelChangesWarning`), so the database tests fail until the migration exists.
- **EF Core 11 migration files have no `<auto-generated>` header** (the designer and snapshot files do) and a class name starting with `_<timestamp>`. `.editorconfig` marks `GraderLogic/Data/Migrations` as `generated_code`, otherwise the analyzers fail the build. Do not edit generated migrations to satisfy analyzers.
- **The design-time factory runs in the project folder** (the tools set the current directory to the startup project's folder, not the shell's). Relative SQLite paths would resolve inside `GraderLogic`.
- **SQLite enforces foreign keys by default** only because the bundled native library is compiled with `SQLITE_DEFAULT_FOREIGN_KEYS`. EF Core does not send `PRAGMA foreign_keys`. The sqlite3 CLI has them off by default (`PRAGMA foreign_keys = ON;` before manual changes).
- **EF Core checks some constraints before the database does.** Deleting a principal whose dependents are tracked fails in EF Core with an `InvalidOperationException`. Tests for database constraints must use a fresh context without tracked dependents (see `GraderTests/Data/DatabaseConstraintTests.cs`).
- **Constraint violations** surface as `DbUpdateException` with a `SqliteException` (error code 19, `SQLITE_CONSTRAINT`) as inner exception. Do not rely on the extended error code: `ON DELETE RESTRICT` reports `SQLITE_CONSTRAINT_TRIGGER`, not `SQLITE_CONSTRAINT_FOREIGNKEY`.
- **Text comparison is case-sensitive** (SQLite's default `BINARY` collation), so unique names like `1a` and `1A` do not conflict.
- `DateOnly` is stored as `TEXT` (`yyyy-MM-dd`), which sorts and compares correctly.
