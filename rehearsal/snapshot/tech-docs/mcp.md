# MCP Servers

Grader offers its use cases as tools for AI agents over the Model Context Protocol (MCP), in two servers with the same tools:

- **`grader mcp`** (`GraderCli`): stdio server, a local process that calls the Web API over HTTP. For agents on a machine with the CLI installed.
- **The Web API at `/mcp`** (`GraderApi`): Streamable HTTP server. Agents connect to a URL; nothing to install.

The concepts and the protocol are documented at https://modelcontextprotocol.io/llms.txt; we support spec revision 2026-07-28. Both use the official C# SDK: `ModelContextProtocol.Core` in the CLI, `ModelContextProtocol.AspNetCore` in the API (see its docs in the `modelcontextprotocol/csharp-sdk` repository).

## What both servers share

- **The same tools:** one per use case of the API, named `<area>_<verb>` (`classes_get`, `demo_data_replace`), with the same descriptions (incl. error codes), annotations, order and server instructions. Ids are integer parameters in camelCase (`classId`), documents a JSON object `document` in the shape of the API's request. `McpEndpointTests.ListTools_SameToolsAsCliMcpServer` compares the tool lists of both servers, so change both together.
- **Annotations instead of confirmation:** read tools are `readOnlyHint`; `save`, `delete` and `demo-data replace` are `destructiveHint` (save replaces lists and removes entries), `create` is not; `save` is `idempotentHint`; all are `openWorldHint: false`. Asking the user before destructive calls is the MCP host's job.
- **Results are the API's JSON** (with explicit nulls, e.g. a missing result), or a confirmation text for use cases without response body (`Deleted class 7.`).
- **Errors are tool errors** (`isError: true`) whose text is JSON with `code`, `message`, `status` and, for `validation-failed`, `errors`, so the model can correct its call. Only unknown tool names are protocol errors.
- **Deterministic tool order** (for clients caching the list): both servers use list/call handlers instead of the SDK's tool collection, which is a dictionary.
- **Stateless, current revision only:** no state between tool calls. The SDK negotiates 2026-07-28 (`server/discover`, per-request `_meta`); clients on older revisions still work through the SDK's `initialize` support, but we write no code for them. Tests use clients pinned to 2026-07-28.

## How they differ

| | `grader mcp` | Web API `/mcp` |
|---|---|---|
| Transport | stdio, launched by the client | Streamable HTTP, stateless (`HttpServerSessionMode.Stateless`) |
| Calls | the Web API over HTTP (Kiota, `ApiCaller`) | the `GraderLogic` services directly, like the endpoints |
| Tools defined by | the CLI's `UseCase`s (one per command, see [cli.md](cli.md#mcp-server)) | tool classes `GraderApi/<Area>/<Area>Tools.cs` and `GraderApi/Mcp/ToolCatalog.cs` |
| Schema of `document` | the request schema from the OpenAPI spec | generated by the SDK from the request record |
| Documents | inline (`document`) or as local file (`file`) | inline only |
| Own error codes | the CLI's (`invalid-input`, `api-unreachable`) | the API's (`invalid-request`, `validation-failed`) |
| Unknown parameters | `invalid-input` | ignored |
| Unexpected errors | `unexpected-error` with the message | the SDK's generic tool error without details (logged), like a 500 |

## The Web API's server

- **Tool classes are plain:** one per use-case area next to the endpoints (`ClassManagementTools`, ...), with `[Description]` on methods and parameters and no MCP types, parameters or logic, so an in-app agent can reuse them (e.g. with `AIFunctionFactory`). Like endpoints, they are thin and call the service. They are scoped services, resolved per tool call from the HTTP request's services (the `DbContext` is per request, as for endpoints).
- **Tools validate documents themselves** with `RequestValidator`, because no endpoint filter runs for them. It uses the metadata the validation source generator creates for the endpoints, so rules and error keys (`Students[0].LastName`) are the same. It throws if a type has no metadata (only types in endpoint signatures get some).
- **MCP specifics live in `GraderApi/Mcp`:** `ToolCatalog` (tool names, annotations, order), `ToolErrors` (exceptions to tool errors), `McpServerSetup` (registration, handlers, instructions).
- **The endpoints' JSON options** (`JsonOptions`) serialize tool arguments and results, so arguments are read like request bodies (required constructor parameters, strict numbers) and results are written like responses (explicit nulls). The SDK's defaults would omit nulls and accept numbers as strings.
- **Error mapping:** `GraderLogicException` → its code and the HTTP status of the problem details; `RequestValidationException` → `validation-failed` with field errors; arguments that do not bind (missing parameter or property, wrong type, `null` document; `ArgumentException`, `JsonException`) → `invalid-request`; anything else → the SDK's generic tool error.
- **Not in the OpenAPI spec** (`ExcludeFromDescription`): it is no REST endpoint, and the API clients must not change.
- **No authentication**, like the rest of the API: whoever reaches the API can call every tool, incl. `demo_data_replace`.

## Connecting a client

**Web API:** the URL is the API's origin plus `/mcp`: `http://localhost:5100/mcp` for the development API, `http://localhost:5200/mcp` for the production-like setup (see AGENTS.md). The Angular dev server (port 4200) only proxies `/api`.

```bash
claude mcp add --transport http grader http://localhost:5100/mcp   # Claude Code (current project)
```

```json
{ "mcpServers": { "grader": { "type": "http", "url": "http://localhost:5100/mcp" } } }
```

**`grader mcp`:** the client launches it as a subprocess. Install the global tool first (see [cli.md](cli.md#building-installing-and-updating)); set `GRADER_API_URL` if the API does not run on the default URL.

```bash
claude mcp add grader -- grader mcp                                           # Claude Code (current project)
claude mcp add grader -e GRADER_API_URL=http://localhost:5200 -- grader mcp   # another API
```

```json
{ "mcpServers": { "grader": { "command": "grader", "args": ["mcp"], "env": { "GRADER_API_URL": "http://localhost:5100" } } } }
```

During development without installing: build once and use `"command": "dotnet", "args": ["run", "--no-build", "--project", "<repo>/GraderCli", "--", "mcp"]`. Without `--no-build`, every start builds (slow startup, and build output would go to stdout).

Test either server interactively with the MCP Inspector: `npx @modelcontextprotocol/inspector grader mcp`, or start it without arguments and enter the `/mcp` URL with transport "Streamable HTTP". Agents doing a teacher's tasks with the tools use the `grader-cli` skill.

## Testing

Tests connect the SDK's `McpClient` to each server in memory: `McpServerRunner` runs `grader mcp` with pipes as stdin/stdout, `ApiMcpClient` connects to `/mcp` through the `HttpClient` of `GraderApiFactory`. See [testing.md](testing.md).

## Gotchas

- **The SDK appends "Returns: …" to tool descriptions**, taken from the `[Description]` of the result type, unless the tool uses structured content. `ToolCatalog` resets the description to the method's, as in `grader mcp`.
- **`GET /mcp` outside of Development returns the Angular app's `index.html`:** a stateless server maps only `POST`, so the SPA fallback answers other methods. 2026-07-28 clients only `POST`.
- For the stdio-specific gotchas (stdout, closing stdin), see [cli.md](cli.md#gotchas).
